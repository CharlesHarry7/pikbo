## 1. 先做出的项目判断

Pikbo 不是一个需要从第 1 周重新启动的通用出海项目。它已经完成了定位、第一版
产品闭环、部分 SEO 基础和真实模型调用验证，当前真正缺的是：

1. 用真实设计玩具卖家验证 ICP、任务频率、可发布质量和付费意愿；
2. 关闭 T5 持久账户/积分和 T6 服务端水印交付两个硬门；
3. 用 10–20 名私人 Beta 用户验证第二个 SKU、导出、复用和单位经济；
4. 只有证据通过后，才评审支付和公开发布。

因此：

- 通用任务表中的“跨境电商实物履约线”目前不套用到 Pikbo；
- “软件/AI 产品线”保留，但按项目现状压缩成下面的 8 周 Gate；
- 已完成的研发不重新做，只补证据、硬门和商业闭环。

## 2. 两套系统如何分工

| 信息 | 唯一事实源 | 更新时点 | 规则 |
|---|---|---|---|
| 代码、配置、CI、测试 | GitHub PR / commit | 每次交付 | 未 push 的工作视为不存在 |
| 开发任务状态 | [`STATUS.md`](../STATUS.md) | 开工、交付、阻塞时 | 不在飞书复制第二张研发看板 |
| 工程交接与可复用结论 | [`HANDOFF.md`](../HANDOFF.md) | 每个有效交付 | 最新记录放最上面 |
| 老板决策、ICP 证据、访谈、合规意见 | 飞书知识库 | 发生当天 | 保留原话、来源、日期和责任人 |
| Gate 结论 | 飞书决策记录 + 本文件摘要 | 每次 Gate 评审 | 必须写继续、调整或停止 |
| 增长实验与 GSC 证据 | `docs/growth/**` | 每次实验 | 仍按现有 Agent Bus 同步 |

连接规则：

1. 飞书的 `00 项目总览` 固定回链本文件、`STATUS.md` 和当前主 PR。
2. GitHub PR 使用仓库 PR 模板填写“Gate”和“知识库/决策链接”。
3. 访谈原文、个人信息、合同和敏感附件不进入公开仓库；GitHub 只放脱敏结论。
4. 任何密钥、邮箱名单、付款资料和客户素材都不得写入飞书公开页或 GitHub。
5. 冲突时，代码状态以 GitHub 为准，业务决策以最新有日期的飞书决策记录为准。

## 4. 8 周执行 Gate

以下数值是首轮验证门槛，不是市场事实。第一批 10 名有效用户结束后必须用真实
基线重新校准。

| Gate | 周期 | 必须交付 | 暂定通过条件 | 当前状态 |
|---|---|---|---|---|
| G0 连接完成 | W1 | GitHub 桥接文档、任务映射、PR 模板；飞书空间与回链 | 两边能互相打开；任务状态只维护一份 | GitHub 已交付，飞书待接入 |
| G1 ICP 证据 | W1–W2 | 12–16 次访谈、反例、3 名设计伙伴 | 同一高频任务在不少于 5 次访谈重复出现；至少 3 人愿持续试用自己的素材 | 未开始 |
| G2 产品可交付 | W1–W3 | 当前产品 PR 决策；T5、T6、关键路径回归 | 账户/积分跨会话可恢复；免费交付是可验证水印文件；失败与退款不撒谎 | 进行中 / 有阻塞 |
| G3 私人 Beta | W3–W5 | 10–20 名目标卖家、20 个 Launch Pack、周访谈 | 可发布输出率 ≥60%；生成→导出 ≥30%；阻断缺陷为 0 | 未开始 |
| G4 商业验证 | W5–W7 | 价格访谈、测试支付、每个可接受输出成本 | 至少 5 次价格访谈、3 个明确付费信号；单位毛利为正或有清晰修正方案 | 未开始 |
| G5 发布决策 | W8 | 产品、增长、合规、客服和回滚包 | 所有 P0 风险有负责人；老板书面选择 GO / ADJUST / STOP | NO-GO |

### Gate 证据定义

- **可发布输出率：** 由用户确认可以直接发布或只需轻微编辑的输出数 ÷ 完成输出数。
- **生成→导出：** 发生真实导出行为的有效生成会话 ÷ 有成功结果的有效生成会话。
- **第二 SKU 率：** 首次成功后的 14 天内，处理第二个不同 SKU 的有效用户占比。
- **付费信号：** 测试支付、签署付费试点、明确接受价格并约定付款日期；“觉得不错”不算。
- **单位毛利：** 实收或测试价格减去模型、存储、转码、支付、退款和人工支持成本。

## 6. 现在、下一步、以后

### 现在：不能绕过

1. 对当前产品收口 PR 做明确决策，避免主分支和长期草稿继续分叉。
2. 关闭 T5：Supabase schema、身份、钱包、任务与积分需要生产级端到端证据。
3. 关闭 T6：生成自有衍生文件，完成真实水印烧录、存储和受控下载证明。
4. 同步招募设计伙伴，不能等工程“全部做完”才开始访谈。
5. 确保 `upload_ready → generate_start → generate_result → export_click → second_sku`
   漏斗可观察。

### 下一步：用用户行为决定

- 把 3–5 个真实高频配方做成默认 Seller Pack，而不是继续扩功能架子；
- 根据可发布输出率和失败原因优化 recipe、质量检查和重试；
- 用第二 SKU 和付费信号判断是否值得启用正式支付；
- 只把有真实证据的案例替换到官网，不制造用户故事或假 UGC。

### 以后：通过 G4 后再评估

- 更高 ARPU 店铺工作流；
- 团队账户、API、白标；
- 创作者网络或模板市场；
- 更多模型和非视频产品面。

这些方向不能进入当前主导航，也不能抢占 T5、T6、Beta 的资源。

## 8. 每周运行节奏

- **周一：** 项目负责人更新 Gate、本周唯一目标和 `STATUS.md` 对应行。
- **周中：** 工程只通过 PR/commit 推进；用户研究当天进入飞书。
- **周五：** 用 [`WEEKLY_REVIEW_TEMPLATE.md`](./WEEKLY_REVIEW_TEMPLATE.md) 复盘指标、原话、风险和决策。
- **Gate 日：** 形成飞书决策记录，并在本文件或 `HANDOFF.md` 留一行脱敏摘要与链接。
- **任何时候：** 没有证据就写“未知/待验证”，不得把计划写成已完成。
